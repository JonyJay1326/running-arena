# 弹弹高尔夫：写一个高尔夫 Bot

任务书版本：2026-11-14-v5（3 次固定练习 + 3 次自定义实验）；第一轮最早第 50 分钟交卷，只用于配套新批次。

你正在与另外 **15 个大模型**参加同一场比赛，所有选手遵守相同规则。你的目标是在规定开发时间内，尽可能降低两轮正式比赛的总计分，争取更高名次。

你要在 **60 分钟** 内写一个程序（Bot），让它控制一名角色用炮弹打“高尔夫”。Bot 会在若干个**事先不公开**的球洞上比赛，地形各不相同，杆数越少越好。

## 规矩

- **只在当前文件夹里工作。** 不要读取、搜索或修改这个文件夹以外的任何文件，不要访问网络（唯一例外：通过发给你的 `probe.mjs` / `practice.mjs` / `lab.mjs` / `check.mjs` / `clock.mjs` 连接其中配置的本机 `127.0.0.1` 试测服务）。不要扫描其他端口或访问其他服务。
- 只用 Node.js 22 或 Python 3 标准库，不要安装依赖。
- 交付：`bot/main.mjs`（或 `bot/main.py`），以及 `NOTES.md`（格式见文末「NOTES.md 格式」）。
- 正式运行只复制 `bot/`，依赖的辅助模块、静态参数文件也须放在其中。`NOTES.md`、试射记录和本地测试脚本供开发与复核使用，不会自动提供给正式运行的 Bot。
- 结束前务必跑一次 `node check.mjs`。验收只检查初始化和首个动作，分别限时 5 秒和 1 秒。

## 比赛规则

- 每洞有标准杆 `par`（1～6）和杆数上限 `cap = par + 4`。**每次开炮或使用纸飞机算 1 杆**，不管选哪种弹；飞机成功或失败都计杆。完成洞按实际含罚杆杆数计分，最高记 `par + 3`；未完成记 `par + 4`。达到 `par + 3` 后仍可继续尝试。当前动作完整结算后，若目标已完成或含罚杆杆数达到 `cap`，本洞结束。最后一个动作产生的罚杆可能使实际杆数超过 `cap`，主控仍完整记录，Bot 观测中的 `strokes` 最高显示 `cap`。
- 每洞的完成条件 `goal`：
  - `tokens`：把场上所有 token（`token` / `bigToken` / `pushToken`）打碎；
  - `bug`：把 Bug 推进回收站区域 `recycle`（Bug 静止时圆心在区域内）；
  - `both`：两者都要。
- 场上未退场、未回收的物体会挡炮弹，炮弹撞上即爆炸：
  - `token`（28×28）：受到任何伤害即碎。
  - `bigToken`（44×56）：血量以当前观测的 `hp`/`maxHp` 为准，不保证是默认 240 血，打空才碎。
  - `pushToken`（滑板 token，30×30）：血量以当前观测的 `hp`/`maxHp` 为准，不保证是默认 150 血。挨炸会掉血，**也会被推走、落地滑行；运动参数不保证与 Bug 相同，具体数值不公开**。打空或掉出地图都算碎。小心把它推进坑里。
  - `chicken`（尖叫鸡，26×30）：**人质**。只要被炸到或掉出地图，**罚 1 杆**，然后它晕倒退场。
  - `bug`（半径 14 的圆）：打不坏，会被爆炸推走（离爆炸越近推得越远；具体数值不公开），之后会落地、沿地面滑行到停下。Bug 掉出地图：罚 1 杆，放回这一杆之前的位置。
- 东西脚下的地形被炸空会往下掉；token 掉出地图算打碎。
- 任何一杆之前都可以声明“不可打”`{"unplayable":true}`：罚 1 杆，尚未回收的 Bug 放回本洞初始位置（地形不恢复）；已经回收的 Bug 不重置。
- 每洞开始站在发球台 `tee:{x0,x1}` 里，每杆前可以在这个范围内走到任意能站稳的位置（`moveX`）。部分洞提供 1 次纸飞机，剩余次数看观测顶层 `fly`，为 0 时不能使用。每次使用计 1 杆并消耗一次机会；成功落地后发球台失效，后续不能再传 `moveX`；出界或无合法落脚点时留在原站位，仍计杆、扣次数。
- Bot 的非法动作、协议错误、响应超时或崩溃会结束当前球洞，该洞按未完成记 `par + 4`，并记录原因。主控机器或引擎故障由主控核实处理，不作为 Bot 能力失分。
- 比赛洞会用到上面的各种弹种和物体机制（连发的先后顺序、爆炸把东西推向哪边、地形被炸开等），**风只是其中一个因素**，各洞侧重点不同。

本届不使用开关和门，无需实现相关策略。

**场景范围：**练习洞不代表正式洞的全部地形。Bug 和各类 Token 不保证位于平地，也可能位于不同高度的平台或复杂地形上。请结合每杆的地形、物体位置和状态决策，不要默认练习洞中的地面高度、支撑条件或运动结果适用于所有场景。

Token 可能被地形遮挡，回收区也可能部分或全部被地形覆盖；回收区标记只表示判定范围，不会自动清除其中的地形。

## 世界和物理（已知部分）

- 世界 1600×900 像素，**y 轴向下**（y 越小越高）。地形是 400×225 的格子，每格 4 像素，`terrain.rle` 是按行展开的 `[值, 个数]` 游程编码（1 = 实心）。
- 角色：`actor.x` 是脚下中心的 x；`actor.y` 是内部参考点，**脚底 = actor.y + config.BODY.footOffset**。炮口在脚底沿身体法线方向往上 `BODY.muzzleHeight` 的位置。站在斜坡上身体会倾斜 `groundAngle`（度）。
- 开炮：`angle` 0～85（相对身体），`power` 0～100，`dir` 为 1（选右）或 −1（选左）。实际发射角 = `angle + dir × groundAngle`，散射的各发还要叠加各自的角度偏移。发射瞬间的水平速度方向由 `dir × cos(实际发射角)` 的符号决定。陡坡上的合成角超过 90° 时，炮弹可以朝所选方向的反侧飞出。
- 炮弹受重力，受风（只影响水平方向）。**重力、力度对应的初速、风的强度系数都不公开。**
- **风**：每洞一个显示风力 `hole.wind`（−8～+8，正数向右，**可能为 0**），整洞不变。**显示的风力是参考值；实际风的强度与高度有关，高空可能比低空更强。** 具体变化规律不公开。
- 纸飞机：`angle` 为相对水平的 0～90°（不叠加身体倾角），`power` 0～100，`dir` 为 ±1。由炮口发出，受相同的重力和风；不撞物体、不造成爆炸，碰到地形后尝试落脚。
- 四种弹（同一个发射器）：

| `kind` | 发射 | 每颗伤害 | 坑半径 |
|---|---|---:|---:|
| `single` 普通单发 | 一颗 | 120 | 32 |
| `burst` 三连发 | 三颗，间隔 0.8 秒，同一角度力度 | 65 | 26 |
| `spread` 三叉散射 | 三颗同时，角度 −6° / 0° / +6° | 55 | 24 |
| `dig` 掘进弹 | 一颗，撞地即爆、坑大伤害低 | 30 | 60 |

  伤害半径都是 30，按距离线性衰减；隔着地形不受溅射伤害。

### 自定义实验（3 次）

```powershell
node lab.mjs experiment.json
```

`experiment.json` 包含实验计划 `plan` 和场景 `scene`（以下仅为格式示例，不是建议的实验）：

```json
{
  "plan": {
    "question": "这次实验想回答什么问题",
    "prediction": "运行前的预测，尽量写出方向和大致数值",
    "decision": "什么结果会让你改变哪项判断或代码"
  },
  "scene": {
    "tee": {"x0": 200, "x1": 340},
    "goal": "tokens",
    "fly": 0,
    "recycle": null,
    "terrain": [{"op": "fill", "rect": [720, 680, 880, 780]}],
    "objects": [{"type": "pushToken", "x": 500, "y": 780, "hp": 150}]
  }
}
```

- **计划**：`question`、`prediction`、`decision` 三项必填，各 1～1000 字符，主控在启动 Bot 前留存。文字不自动评分，预测错了也不罚。
- **场景固定无风**：`wind` 可省略，写了只能是 0。风只能通过试射测定。
- **地形**：从平地（地面 y = 780）开始，最多 8 个图元，按顺序施加。`op` 为 `fill`（填实）或 `carve`（挖空），形状三选一：
  - `rect: [x0, y0, x1, y1]`：矩形，坐标是 4 的倍数，边长至少 4；
  - `circle: [x, y, r]`：圆，整数，`r` 为 8～300；
  - `ramp: [x0, y0, x1, y1, yEdge]`：斜坡，即 `x0`～`x1` 之间、斜线 (x0, y0)→(x1, y1) 与水平线 `y = yEdge` 之间的区域；`x0`、`x1` 是 4 的倍数，宽至少 8，坐标为整数。例如 `{"op":"fill","ramp":[600,780,800,700,780]}` 在平地上堆出一个向右升高 80 像素的坡；`carve` 加 `yEdge` 取在斜线上方，可以把平台边缘削成坡。
  - 地形都在 1600×900 地图内、按 4 像素格子取格心生效，所以斜坡实际是细台阶，与正式地图的格子精度相同。斜坡展开后的段数有上限，过宽或过多的斜坡会被拒绝（不扣次）。自建场景仍是简化地形，验证通过的结论不一定适用于正式洞。
- **物体**：1～6 个，类型为 `token` / `bigToken` / `pushToken` / `bug` / `chicken`，其中 Bug 最多 1 个；字段只有 `type`、`x`、`y`（底部中心）和 `hp`（仅 `bigToken` / `pushToken`，1～2000）。放置时，物体若嵌入地形不超过 16 像素会先向上抬出，然后落到正下方第一个支撑面上，所以在坡上不必算准 y；正下方没有支撑、或嵌入更深会被拒绝（不扣次）。实际初始位置以返回的 `initial` 观测为准。
- **其他**：`tee` 为 `{x0, x1, minFeet?}`，须有能站稳的位置；`goal` 为 `tokens` / `bug` / `both`，需要 Bug 时须给回收区 `recycle: {x0, y0, x1, y1}`，不需要可为 `null`；`fly` 为 0 或 1。初始状态不能已经完成目标。不接受其他字段（如地图名、地形编码、物理参数、杆数上限）。
- 每次最多 5 杆（含罚杆），目标完成即结束；场景内部使用的 par/cap 仅为运行上限，不计分。
- 动作完全由你当前的 Bot 根据观测决定，接口不接受动作列表。除共同规则中的内容外，还返回初始观测 `initial`（含地形、站位倾角和物体位置）。结果同时追加到 `lab.local.jsonl`。

## 协议（JSON Lines，stdin/stdout）

每洞会从当前工作目录启动 `node bot/main.mjs` 或 `python bot/main.py`，Bot 在该洞内是常驻进程：每行读入一个 JSON，每行写出一个 JSON；stdout 只写协议，调试信息写 stderr。

1. 初始化：收到 `{"type":"init","reqId":…,…观测…,"config":{…}}`，**5 秒内**回 `{"reqId":同一个,"ok":true}`。
2. 每杆前：收到 `{"type":"turn","reqId":…,…观测…}`，**1 秒内**回下面三种之一（不能有多余字段）：

```json
{"reqId":2,"moveX":460,"attack":{"kind":"single","angle":30,"power":50,"dir":1}}
{"reqId":3,"fly":{"angle":45,"power":50,"dir":1}}
{"reqId":4,"unplayable":true}
```

`moveX` 可省略（不动）；飞机成功后必须省略。观测字段见 `sample-observation.json`（协议样例，不代表练习洞或正式洞的具体设置）：

- `hole`：`id, map, par, cap, wind, goal, recycle, tee, teeActive`。
- `hole.tee`：`{x0,x1,minFeet?}`，可选的 `minFeet` 是合法站位的脚底高度下限；有多层地形时不能默认站在最上层。`teeActive` 为 false 时不能传 `moveX`。
- 顶层计数：`strokes` 为当前含罚杆杆数（观测值最多显示 `cap`；实际含罚杆杆数另外记录），`penalties` 为罚杆数，`shotsTaken` 只统计开炮次数（不含飞机和不可打），`fly` 为剩余飞机次数。
- `terrain`、`actor:{x,y,groundAngle,grounded}`
- `objects:[{id,type,x,y,width?,height?,radius?,hp?,maxHp?,stage,removed,broken,stunned,inRecycle}]`，坐标是物体**底部中心**（Bug 是圆底）
- `lastResult`：上一杆的结果 `{action, command, from, impacts:[{projectileId,kind,x,y,hit,objectId}], objectChanges:[{id,before,after,damage}], penalties:[{reason,objectId}]}`。**只有落点和变化，没有轨迹。**

**提示：** 用 `lastResult.impacts` 对照预测落点，结合目标的位置、血量以及新观测里的地形判断进展。目标没有变化时，落点逐步深入且通道正在打开，仍可能值得继续。如果连续两次既没有推进目标，也没有打开可用通道或改善落点，可以换站位、弹种或路线。

同一个 Bot 进程会连续打完一洞；不同洞是不同进程，普通内存变量不会保留，**正式跑洞期间不会再给你试射**。开发时学到的参数可写进 `bot/` 下的代码或数据文件；运行中积累的经验可用下面的运行时笔记本传递。

### 统一考卷（比赛前，不计入成绩）

比赛开始前，你的 Bot 会单独启动一次，直接收到一条考卷消息，**此前不会发送 `init`**；所需公开配置在考卷消息的 `config` 中：

```json
{"type":"exam","reqId":1,"config":{…},"ground":780,"questions":[{"id":1,"wind":5,"x":300,"angle":20,"power":80,"dir":1}, …]}
```

题目都在平地上（脚底 y=780，站在 x 处开炮，同试射场）。请在 **5 秒内**回一行：

```json
{"reqId":1,"predictions":[{"id":1,"x":922.4,"y":780.1}, …]}
```

用你推出的物理预测每题的落点。答满 12 题的 Bot 按平均水平误差排名，部分作答也会记录答题数和误差。考卷成绩不计入正式排名。

### 运行时笔记本（可选的跨洞记忆）

`NOTES.md` 是必交的开发记录，供复核实验、推断和改动。`bot/memory/` 是 Bot 在比赛运行时可选读写的目录，两者用途不同；主控不会自动把 `NOTES.md` 的内容变成 Bot 的记忆。

- 比赛时 9 个洞按**固定顺序**依次进行（所有选手顺序相同）。
- Bot 可以在 `bot/memory/` 文件夹里读写文件（相对 Bot 的工作目录，即本文件夹）。**这个文件夹会原样保留到下一洞**，你可以把前面几洞学到的东西（比如落点偏差、Bug 推力的实测效果）记下来，后面的洞继续用。
- 比赛运行中的 Bot 只能写 `bot/memory/`，不要改其他文件；开发阶段仍可编辑程序和开发记录。笔记本写坏了导致后面出错，后果自负。
- 目录会跨洞保留，但不会自动记录每洞信息。写入、追加、覆盖以及后续读取和使用哪些信息，由 Bot 自己实现；仅写日志不等于利用了跨洞记忆。
- 不实现跨洞记忆也完全可以，本身不算缺项；第二轮的携带内容限制以届时任务书为准。

## 时间

开发预算为 **60 分钟**。试射、推断物理、写代码和验证各用多久，由你自行决定。

**你的目标是在开发预算内尽可能降低正式比赛总计分，不只是完成一个能通过检查的程序。** 通过 `check.mjs` 或用完试射、练习或实验额度，不代表开发已经完成；仍可进行本地测试、分析已有记录并改进策略。最早交卷时间只是允许提交的下限，不是建议结束时间。是否提前交卷由你判断，请在 `NOTES.md` 中简述理由和仍未验证的风险。无需为了用满时间而盲目修改已经验证有效的代码。

初版可运行后，请继续找出最影响成绩、尚未验证或未解决的问题，利用剩余时间做有明确目的的验证或修正，不要仅为等待最早交卷时间而停止工作。决定停止主动开发（包括启动计时器等待可交卷时间）前，请检查当前最可能影响正式成绩、仍缺乏证据的一项风险；若存在能在剩余时间内完成且有判别力的检查，先完成它。检查可以只分析现有记录或代码，不必修改程序。记录该风险、检查结果，以及继续验证或修改为何不值得。若获准资源不足以验证，就明确保留为未知；“额度用完”“自测全过”或“继续修改有风险”不能单独作为停止依据。不要求重复无新增价值的测试，也不要求突破时间或资源限制。

**优先做出可参赛的 Bot。** 即使还没推准物理，也先实现一个能根据当前观测给出合法动作、能通过 `node check.mjs` 验收的版本，再用剩余时间提高命中率。

**随时运行 `node clock.mjs` 看时间**：它会显示你的开发开始时间（以主控登记为准，不要用系统时间自己推算）、已过几分钟、什么时候可以交卷、离截止还有几分钟。

- 第 **30** 分钟和第 **50** 分钟：主控会发一条剩余时间提醒（只报时间）。
- **最早第 50 分钟交卷**：第 50 分钟前不要宣布完成，提前写完就继续测试、改进；第 50～60 分钟之间可以随时交卷，60 分钟必须停。
- 申请提前交卷后停止编辑和测试，等待主控确认时间并冻结。开发截止后不能新开试射、练习、自定义实验或检查；跨截止的练习或实验会被停止，仍扣一次，不返回超时结果。
- 请在截止前通过 `node check.mjs` 并写好 `NOTES.md`，到时间停止开发。

## NOTES.md 格式

请按下面五节写（每节简短即可）：

1. **试射计划**：保留第一发前写下的初始计划，列出计划使用的发数、各阶段的分配及要验证的问题。
2. **试射复盘**：每一发一行——目的 / 预测 / 实际落点 / 由此得出或修正了什么。若调整计划，注明促成调整的试射编号、实际结果及接下来要验证的问题。
3. **我推出的物理**：用公式写出你最终认定的模型——发射点、初速与力度的关系、重力、风的大小、风随高度怎么变化。写清楚哪些是测出来的、哪些是猜的。
4. **练习与实验复盘**：每次固定练习或自定义实验一行——类型和编号 / 当时 Bot 是哪一版 / 自定义实验的问题和预测 / 看到了什么（落点、物体往哪边动、掉了多少血）/ 据此改了什么，或为什么不改。没用某类额度就写“未使用”和原因。
5. **Bot 策略、实现状态与已知不足**：说明如何选弹种、站位和瞄准，以及哪里可能出问题。如果实现了纠偏或跨洞学习，简述各自如何工作。列出最终实现的主要功能，每项简述作用、对应代码位置及验证情况（已验证／仅实现未验证／已知无效或有缺陷）；已验证的注明证据来源、结果和适用范围；仅通过自造模拟的标明“本地模拟通过，真实效果未验证”。列出考虑过但未实现或中途放弃的功能，并说明原因；未考虑过的无需补列。每项一行即可。若提前交卷，简述停止开发的理由和仍未验证的风险。
